# Releasing

There is no Xcode project. `Scripts/bundle.sh` turns the package executable into something macOS treats as an app. Without a bundle there is no `Bundle.main` (no version for the update check, no `SMAppService` login item — hence the launch-agent fallback), and nothing to hand anyone but a build folder.

Toolchain and local `swift build`: [build-from-source.md](build-from-source.md). Why the bundle exists and how defaults migrate: [decisions/bundle-and-defaults.md](decisions/bundle-and-defaults.md). Changelog vs Sparkle: [decisions/release-notes-in-changelog.md](decisions/release-notes-in-changelog.md).

## Version and tag

The version lives in `VERSION` and nowhere else. Tag `v$(cat VERSION)`. The update check reads GitHub’s latest release tag against `CFBundleShortVersionString`.

**Pushing a tag is the whole release.** Both `CHANGELOG.md` and `CHANGELOG.zh-CN.md` need a `## x.y.z` section **before** the tag: the workflow stops without either, before it builds. GitHub Release notes are **bilingual, Chinese first**, built by `Scripts/release-notes.py`. Sparkle's update window uses **Chinese** `CHANGELOG.zh-CN.md` first (English `CHANGELOG.md` as fallback). Generating notes from commit subjects is a fallback for forgotten English entries in older tooling, not the path for a tagged release.

```bash
# CHANGELOG.md and CHANGELOG.zh-CN.md first. Then:
echo 1.0.1 > VERSION && git commit -am "Blinky 1.0.1"
git tag v1.0.1 && git push && git push origin v1.0.1
```

The feed URL and the download links are taken from `GITHUB_REPOSITORY` in CI, or from `origin` on a local Mac. A fork therefore publishes to **its own** Releases and `appcast.xml`, not to upstream's. The Sparkle private key is per-repo (`SPARKLE_PRIVATE_KEY`); a fork needs its own, because the public half is baked into the app at bundle time.

A tag/VERSION mismatch fails the run. A suffix (`v1.1.0-beta.1`) is a GitHub pre-release, excluded from “latest,” so the in-app check ignores it too — **and the workflow does not write it into the Sparkle feed**, which has no beta channel: an item there reached every installed copy as an ordinary update. **Re-running a release replaces its download in the feed.** The Publish step re-uploads the zip with `--clobber`, and a rebuilt zip is not the old bytes, so `Scripts/appcast.py` rewrites that version's `<enclosure>` (URL, length, EdDSA signature) to the new archive; it used to keep the old signature, and Sparkle refused the update. The item's date and notes stay as first published.

## CI

`.github/workflows/release.yml` builds, packages, publishes, signs the archive, and commits the Sparkle feed. `ci.yml` runs the same build on every push.

Both pin **`macos-26`**, not `macos-latest`. `PanelSurface`’s Liquid Glass needs the macOS 26 SDK to compile even behind `#available`. Workflows check `xcrun --show-sdk-version` first. Warnings fail the build.

Release needs `SPARKLE_PRIVATE_KEY`. It fails without it rather than publishing a version no installed copy would be offered.

The Package step builds once. `./Scripts/bundle.sh --zip` produces `build.noindex/Blinky.app` and `Blinky-<version>.zip`. `./Scripts/dmg.sh --reuse` writes the disk image from that app and does not run `swift build`. A local `./Scripts/dmg.sh` still builds, then writes the image.

The debug `swift build` and `swift test` run on Release unless the Build workflow (`ci.yml`) has already succeeded for the tagged commit. That means a finished green run for the same SHA. No run, a failed or cancelled run, or a run still in progress leaves both steps in place. Tag and VERSION agreement, both changelog gates, and the Sparkle signature are unchanged.

## Bundle (`Scripts/bundle.sh`)

- Resource bundle in `Contents/Resources` (`Bundle.module` via `Bundle.main.resourceURL`). Leave it out: English, no provider marks.
- `LSUIElement` = true.
- **Icon: `AppIcon/AppIcon.icon`**, an Icon Composer document, compiled by `actool` into `Assets.car` plus a flattened `AppIcon.icns`; `CFBundleIconName` points at it. The layer is `mascot.png`, the Blinky mascot on its dark squircle. Glass, the group shadow, and translucency are off: the picture is the icon, and a glass treatment would replace the drawing with the shape of its outline. `blinky-icon-1024.png` (README) and the Raycast icon are that picture. The menu bar and the recap header use `blinky-mascot.png` from the resource bundle.
- `CFBundleURLTypes` registers `pulse` for settings/account navigation. The developer kit is copied to `Contents/Resources/Integrations` from an explicit file list: scripts, Raycast source, manifest, lockfile, icon and tests; no `node_modules` or generated extension output. This copy needs no Node.js build on release CI. [integrations.md](integrations.md)
- Universal: `--arch arm64 --arch x86_64`. Zip with **`ditto`**, not `zip` (plain zip flattens bundle symlinks). Release passes `--zip` on this one build, then `./Scripts/dmg.sh --reuse`, so the script does not run again for the archive.
- **The SDK stamp is checked, not assumed.** macOS draws an app's controls to the SDK version in its `LC_BUILD_VERSION`, and below 26 it uses the previous design. `Package.swift` stamps 26.0 in `linkerSettings` — the manifest, not this script, so that a build run from Xcode matches a release — and this script reads it back off **every slice** after linking and refuses to package anything lower. The flag alone is not enough: when SwiftPM last got this wrong there was no error and no failing test, only an app drawn the old way. [decisions/sdk-stamp-and-appearance.md](decisions/sdk-stamp-and-appearance.md)
- **Output is `build.noindex/`.** Spotlight indexes any `.app`; a project-folder build appears beside the installed copy, and whichever is opened claims the login item and rewrites Claude Code’s status-line path to itself. A `.metadata_never_index` marker was tried and did **not** stop indexing (historical); the `.noindex` suffix is what Spotlight honours. Do not rename it back.
- Sparkle is copied into `Contents/Frameworks` and `@executable_path/../Frameworks` is added to the rpath. Sign **inside out** (nested XPC / updater first).
- Ad-hoc signature is **not** distribution signing. It stops macOS calling the bundle damaged when moved. Gatekeeper still warns on first open until Developer ID + notarisation.
- **And every update re-asks for the keychain.** Ad-hoc means no stable identity, so the designated requirement is the binary's own cdhash — `codesign -d -r-` prints `cdhash H"…"`, and `TeamIdentifier=not set`. A keychain item's "always allow" list matches on that requirement, so a rebuilt Pulse is a program the list has never seen and macOS prompts again. It bites because Pulse reads other apps' `Safe Storage` keys to decrypt browser cookies ([providers/README.md](providers/README.md)) — one prompt per browser, on every update. Nothing in the app can suppress it; the ACL is the user's, and the mismatch is real. A Developer ID certificate is the only fix, because it makes the requirement team-based and therefore stable across versions. A self-signed certificate would also be stable, but releases are built in CI, so the private key would have to live there as a secret — the same work for none of the notarisation.

## Disk image (`Scripts/dmg.sh`)

The image is the install guide: Blinky is not notarised, and on macOS 15+ Control-click → Open is gone. Instructions are printed on the window (README-only instructions are not read by people downloading an app).

Finder window layout is a committed `Scripts/dmg-DS_Store` (AppleScript cannot run on CI). Recapture with `./Scripts/dmg.sh --relayout` after changing the backdrop or icon positions. Finder `bounds` **include the title bar** (~28pt taller than a 660×420 backdrop). Backdrop: `Scripts/dmg-background.tiff` (1x and 2x).

`./Scripts/dmg.sh --reuse` packages the existing `build.noindex/Blinky.app` and skips `bundle.sh`. The app's `CFBundleShortVersionString` has to match `VERSION`. Release runs `./Scripts/bundle.sh --zip` first, then this, so the universal build happens once and both downloads are that app.

Sparkle updates from the **zip**, not the DMG. The image is for people.

## Sparkle

The feed title and the heading in the update window say **Blinky**. The bundle identifier stays `io.github.qunqin24.Pulse`. The disk image is `Blinky-<version>.dmg` and the update archive is `Blinky-<version>.zip`, and the app inside them is `Blinky.app`. The executable inside the bundle stays `Pulse`, and the URL scheme stays `pulse`. Items already in the feed keep the archive names those releases uploaded.

**An in-app update renames an installed `Pulse.app` the next time that copy opens.** Sparkle matches the bundle in the zip by file name or, failing that, by bundle identifier (`Autoupdate/SUInstaller.m`: the host file name, then `SUHost.name` + `.app`, then the same bundle id). `Info.plist` sets `SUBundleName` to Blinky, so a copy already named Blinky finds `Blinky.app` in the archive. The install path is separate. `SPARKLE_NORMALIZE_INSTALLED_APPLICATION_NAME` is a compile-time flag, off in the Sparkle framework SwiftPM builds, so the installer still writes the new bundle over `host.bundlePath` and the helper relaunches that path. `updaterWillRelaunchApplication` runs in the process that is quitting, before that write, and cannot aim the relaunch at a new file name. `InstalledAppName` runs on the following launch, before the interface (`PulseMain`, after `LegacyDefaults`), and moves `Pulse.app` to `Blinky.app` in the same folder when `Blinky.app` is absent. It then opens that bundle with `open -n`, registers it with Launch Services, and exits, so the process that stays up has `Blinky.app` as `host.bundlePath` for the next update. Finder labels a file by its name, so the renamed copy shows as Blinky in Finder and Launchpad.

A `Blinky.app` already in that folder stays where it is: a newer copy of this bundle identifier, an older or equal one, a version that is not a dotted number, a bundle whose identifier differs, or a folder with no readable `Info.plist`. The move never replaces it. A translocated launch (`AppTranslocation`) and a `Pulse.app` that is a symbolic link are left alone. `--json`, `--recap`, and the status-line command return before the rename, so a poll does not move the bundle; the next ordinary launch does. `StatusLineHook.repairPathIfNeeded` rewrites Claude Code's status-line command on the relaunched copy, because that command contains the executable path.

The login item stores a path (`SMAppService` the bundle, the launch-agent fallback the executable). When Open at login was on, the launch that is already `Blinky.app` unregisters and registers once (`LoginItem.refreshAfterBundleMoved`, flag `installedAppName.reregisterLoginItem`). If login no longer starts Blinky, turn Open at login off and on under Settings → General. A translocated launch does not consume that flag. Settings and keychain items follow the bundle identifier, which does not change. The executable stays `Pulse`.

`AppUpdate.swift`. Safe without Apple Developer ID because of the **EdDSA** key: Sparkle refuses any archive not signed by the private half whose public half is in `Info.plist`. Apple signing is recommended by Sparkle, not required. Notarisation would only help Gatekeeper on **first** launch, which no updater can fix.

- `SUFeedURL` is only present in a bundle. `AppUpdate` starts nothing on `swift run`. Each check reads **this fork's** files on GitHub (`raw.githubusercontent.com/harrisliangsu/blinky-mac/main/`). Blinky, set to a language, reads `appcast-zh.xml` or `appcast-en.xml` beside `appcast.xml`; one following the system reads `appcast.xml`. The public key is the fork's (`Scripts/sparkle-public-key.txt`). Upstream's **update.qunqin.org** mirror is not a fallback, and the qunqin24 feed is not read. [update-mirror.md](update-mirror.md)
- **Checked every two hours** (`SUScheduledCheckInterval` 7200), against Sparkle's own default of a day. A day suits an app that ships every few months; this one ships fixes for things it is doing wrong now, and somebody burning a core on a bug fixed yesterday should not wait out the rest of the day to be told. Sparkle clamps anything under an hour (`SPUUpdaterSettings.minimumUpdateCheckInterval`) and measures from the **last check** rather than from launch (`SPUUpdater.m`, `intervalSinceCheck < updateCheckInterval`), so relaunching does not re-check and this is at most twelve requests a day.
- **Checking is not installing, until the reader says so.** `SUEnableAutomaticChecks` is true and `SUAutomaticallyUpdate` is false, so a fresh install offers an update and does not apply it. Checks start without Sparkle's permission prompt because this is an `.accessory` app whose panel never becomes key — that prompt opens behind everything and goes unanswered. The toggle lives in Settings instead. **Install silently** (Settings → About → When an update is found) sets `automaticallyDownloadsUpdates` for a scheduled check: Sparkle's automatic driver downloads with no offer window, and when that download finishes `updater:willInstallUpdateOnQuit:immediateInstallationBlock:` returns true and runs the block on the next turn, so Blinky installs and relaunches without waiting to quit. Notify first stays the default. Check now and Check for Updates… still open the window. `SUAllowsAutomaticUpdates` is omitted. Sparkle 2.9 treats an explicit false as a ban that makes `setAutomaticallyDownloadsUpdates` a no-op, so the checkbox cannot be switched off that way. `SparkleAutomaticCheckbox` hides Sparkle's own switch inside the offer window (`SUUpdateAlert`). `NSButton` has no `buttonType` getter; the checkbox is the button that is not bordered, and Install, Later, and Skip are bordered.
- **The offer has to activate the app.** `LSUIElement` is true and the running policy is `.accessory` (`SUApplicationInfo.isBackgroundApplication` is that policy, not the plist key). When Sparkle shows the offer, its standard driver (`setUpActiveUpdateAlertForScheduledUpdate`) does not activate a background app: `showWindow` while this app is inactive, or `orderBack` when it already has a key window. A `.regular` app that is already active can instead wait for a later activation and not show the window at all. `activateIgnoringOtherApps` does not fix it — a permission prompt calls that and still opens behind everything, which is why Sparkle's own permission prompt is not shown. `UpdaterRelay` adopts `SPUStandardUserDriverDelegate`. It implements gentle scheduled reminders (`supportsGentleScheduledUpdateReminders`). **Notify first** (the default, Settings → About → When an update is found) returns false from `standardUserDriverShouldHandleShowingScheduledUpdate`, so Sparkle keeps the offer and does not show it; `standardUserDriverWillHandleShowingUpdate` with `handleShowingUpdate` false posts a notification (`blinky-update`). Clicking that notification, Check for Updates…, and About's Check now call `AppUpdate.check`, and Sparkle's `checkForUpdates` while `showingUpdate` is set calls `showUpdateInFocus` rather than starting a second check. **Show the window**, a refused notification grant, and a grant that comes back denied make Sparkle show the offer immediately, so an update is not lost. **Install silently** does not show the offer and does not post the notice; the automatic driver does the download. Switching to it withdraws a notice already posted and does not reveal a held offer. `immediateFocus` does not change the choice: a scheduled check near launch is still scheduled. Only when the window is actually going up does `willHandle` (`handleShowingUpdate` true) or the reveal path ask `DockPresence` to switch to `.regular` and activate. The offer window (`SUUpdateAlert`, frame name `SUUpdateAlert2`) is then made key on the next turn, after Sparkle's own ordering, and Sparkle's automatic-install checkbox is hidden. `standardUserDriverWillFinishUpdateSession` drops that request and withdraws the notification; Settings or the recap still hold `.regular` when they are open. `SUAutomaticallyUpdate` stays false. About's silent probe (`checkForUpdateInformation`) does not show the window. The decision itself is `UpdateAnnouncement`, which the tests pin without a window server.
- Sparkle’s delegate cannot be main-actor-isolated; `UpdaterRelay` sits between it and the `@Observable` model.
- `didAbortWithError` also fires for the user closing the window; only a genuine feed failure is reported.
- Notes live in the feed `<description>`, **not** `sparkle:releaseNotesLink` (that loads the whole GitHub page in a WebView). If both are present, the link wins — the link must be absent.
- **The update window shows the version being offered.** Sparkle concatenates the `<description>` of every item newer than the installed copy, and each description is already that version's changelog section, so a long feed stacks past releases in the window. The archives are full zips, not deltas. `Scripts/appcast.py` keeps one item (`KEPT_ITEMS`, the newest) in `appcast.xml`, `appcast-zh.xml` and `appcast-en.xml`. The three files on this branch already hold only 1.5.3; the next release replaces that item.
- **One language in the update window.** Each new item carries one `<description xml:lang="…">` per changelog file — Chinese from `CHANGELOG.zh-CN.md` as `zh-Hans` **and** `zh-Hant`, English from `CHANGELOG.md` as `en` — and Sparkle shows the one the **system's** preferred languages pick; Japanese, Korean and Russian get English. Sparkle cannot see Blinky's own language setting, so `appcast.py` also writes `appcast-zh.xml` and `appcast-en.xml` on this fork's GitHub raw URLs, and Blinky, set to a language, reads its copy (`AppUpdate.feedURL(for:base:)`, through `feedURLStringForUpdater:`); one following the system reads `appcast.xml`. The workflow commits all three. `Scripts/appcast.py --notes <version>` rewrites one served item's notes and nothing else (enclosure, signature and date stay).
- Description: spacing only, no colours or fonts. Sparkle injects `ReleaseNotesColorStyle.css`.
- Public key: `Scripts/sparkle-public-key.txt` (committed). Private key: `SPARKLE_PRIVATE_KEY` only.
- `Scripts/appcast.py` signs the zip and writes the three feeds, each with that one newest item. A version the feed does not yet carry replaces it. A version already there has **that item's enclosure** rewritten (`url`, `length`, `sparkle:edSignature`) from the zip just signed; the notes stay. The workflow commits the feed **after** publishing (the feed points at the release asset). Before that push it fetches `origin/main` and rebases the feed commit onto it, and retries a few times if the push is rejected. A merge that lands while the release is still packaging leaves the zip published and the feed on the previous version when this push is rejected (`fetch first`). Repairing that feed by re-running the Release job uploads the zip again with `--clobber`, and a new build is different bytes, so the published archive changes.
- Release runs are serialized (`concurrency` on `release.yml`, `cancel-in-progress: false`). Two runs for one tag — a lightweight tag and then an annotated one — otherwise overlap: the first signs its zip into the feed, the second replaces the GitHub asset with `--clobber`, and a feed that refuses to change leaves Sparkle checking the new zip with the old signature. The waiting run signs the zip it actually published. [decisions/appcast-same-version.md](decisions/appcast-same-version.md)

`Scripts/changelog.py` reads one version entry from `CHANGELOG.md` or (with `--zh`) from `CHANGELOG.zh-CN.md`, as markdown or `--html` for the Sparkle feed. Grammar: bullets, `**bold**`, `` `code` ``, links.

**GitHub Release notes on this fork** are assembled by `Scripts/release-notes.py` (Chinese first, then English), not by upstream's `changelog.py --release-notes`. Each language file carries its own `## x.y.z` section — there are no `**中文**` / `**English**` markers inside a single CHANGELOG entry. The workflow checks that both files have the version section before it builds.
